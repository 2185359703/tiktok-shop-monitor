# 任务状态与故障恢复

持久化执行由 MySQL 管理，消息重复不代表重复执行。所有数据库时间和逻辑窗口使用 UTC。

## 正常与失败路径

```text
pending ──────────> running ──────────> succeeded
retry_waiting ────> running ──可重试──> retry_waiting
abandoned ────────> running ──不可恢复/耗尽──> dead
running ──租约过期──> abandoned ──到期通知──> running
running ──租约过期且次数耗尽──> dead
```

`cancelled` 是已取消的终态；本次运行层不会自动重开已取消、已成功或已耗尽任务。历史种子替换产生的取消记录仍保留。

`attempt_count` 包含首次执行，默认 `max_attempts = 3` 表示最多三次总尝试，不是额外重试三次。分布式处理器的 HTTP 客户端只执行一次网络尝试，重试预算统一交给任务层，避免内外重试叠乘。

商品发现是每页一个任务：`succeeded` 只表示本页处理成功，不表示全店遍历完成。公开原生游标和累计已见 ID 保存在后续任务 payload，`scheduled_for` 沿用根任务窗口。商品、详情任务和下一页任务在同一租约保护事务提交。只有来源 `has_more=false` 才记录 `progress.complete=true`；达到页数预算记录 `page_budget` 且 complete=false。

商品快照任务按资源 + UTC 窗口 + 价格上下文幂等，第一条有效观察保存后不覆盖；商品与当次已见 SKU 快照、后续变化检测任务同事务提交。变化检测可在网站暂停时运行，只有其 SQL 事件写入成功后才确认通知。相同前后快照重复比较不增加事件。

## 领取与心跳

- Worker 按通知中的业务 UUID 查任务，通过行锁确认状态、市场、任务类型、可运行时间和剩余次数。
- 每次领取生成不同的租约 UUID，与 `worker_id` 和本次尝试号一起保存。
- 默认租约 120 秒，心跳 15 秒。配置要求租约至少覆盖三个心跳周期。
- 过期租约不能续期，也不能提交结果。业务 `apply` 前后都检查当前租约。
- HTTP/解析在线程中执行；SQL Session 不跨线程共享，RabbitMQ 操作留在主线程。
- 长分页采集器应定期写检查点；`save_checkpoint` 使用同样的租约栅栏，旧 Worker 不能覆盖新进度。

## 常见故障

| 故障 | 已实现行为 | 数据结果 |
| --- | --- | --- |
| 同一通知重复到达 | 非到期/运行中/终态不重复领取 | 不增加尝试或业务记录 |
| SQL 创建任务后进程退出，尚未发布 | Scheduler 再次扫描到期行 | 任务不会仅因通知缺失丢失 |
| 已发布但确认丢失 | 后续扫描可再次通知 | 唯一键、租约和幂等写入消化重复 |
| Worker SQL 提交后 ACK 前退出 | 消息可重投，任务已成功则跳过 | 已提交结果不再次执行 |
| Worker 请求过程中退出 | 租约到期后恢复为 abandoned 或 dead | 保留检查点和失败尝试 |
| 旧 Worker 晚到的结果 | 租约标识/到期核验失败 | 禁止业务写入与状态覆盖 |
| 网络/可重试 5xx | 指数退避与有界抖动 | 保留逻辑窗口，未耗尽则待重试 |
| 字段校验/身份不唯一 | 回滚业务写入，记录失败耗尽状态 | 不伪造成功或店铺不存在 |
| 401/403/429/安全验证页面 | 市场 Redis 暂停，当前任务进入有界冷却重试 | 不换指纹、不越过认证，不视为下架 |
| Redis 不可用 | 请求闸门关闭，执行不继续请求 | 不退化为无限制抓取 |
| MQ/DB 临时断线 | 进程记录错误类型后重连，未确认消息保留 | 租约与补发机制恢复执行 |

Redis 暂停默认 900 秒，不是保证冷却后目标站一定允许访问；需要结合证据检查。暂停期间未领取任务只调整最早运行时间，不消耗尝试次数。

## 重试与死信

网络退避基准 10 秒，上限 300 秒；按 UUID 与尝试次数生成不超过 20% 的有界抖动。显式的市场冷却时间优先于网络退避。

业务失败信息保存在 `crawl_tasks / crawl_attempts`。RabbitMQ 死信队列记录被拒绝的通知，不是业务失败的唯一凭据。租约恢复判定耗尽时也会在 MySQL 记为 `dead`，但不保证对应通知已经进入 MQ 死信队列。

运行层目前不提供自动重开 `dead/cancelled` 的 HTTP 接口。先排查错误和处理器，再通过明确的补采业务创建新的逻辑任务；不能把同一历史任务次数清零来掩盖失败。

## 排查入口

```powershell
.\.venv\Scripts\python.exe -m scripts.run_scheduler --dry-run
.\.venv\Scripts\python.exe -m scripts.run_worker --check
Invoke-RestMethod http://127.0.0.1:8000/api/v1/tasks?status=dead
```

查看单个任务时，使用 `/api/v1/tasks/{task_id}/attempts`，其中 `task_id` 是 UUID，不是自增主键。返回值不包含密码、完整任务 payload 或手工录入的旧错误原文。

结构化日志只保留任务 UUID、类型、Worker、尝试次数、状态、错误类型和耗时；异常只记录类名，不展开可能包含连接密码的异常字符串。
