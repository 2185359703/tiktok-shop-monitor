# 店铺档案与评论覆盖

安装采集器不代表已有数据。店铺档案必须有周期任务；历史商品需要补建评论任务。

店铺档案使用采集管理中的每日计划，资源为 `configs/shop-profiles.toml` 对应的既有 100 家已核验美国店铺。该计划由现有调度器执行，可在采集管理查看和暂停。不同时启用另一份相同范围的周期计划。

后续成功的商品详情、快照和图片介绍补采，在原有租约保护事务中为没有评论任务、且评价数量未明确为零的商品创建首次评论任务。评价数量未知不等于没有评论。只有启用 `product_reviews` 时才创建；已完成、正在执行和失败耗尽的评论任务均不会被后续详情反复创建。人工评论采集接口仍保留指定页数的功能。

历史数据使用原有异步数据库和 Worker 补齐，命令先只读预览，再执行：

```sh
python -m scripts.enqueue_review_backfill
python -m scripts.enqueue_review_backfill --execute
```

默认范围来自同一份 100 店名单，只选择已采到详情且来源评价数量不明确为零的商品。按店铺轮流入队，分批提交，重复执行不会为已有评论任务再次建任务。`--limit` 可限制本次商品数量。实际 HTTP 请求由现有协程 Worker 按共享 1 秒间隔执行，不增加 Worker 数量。

匿名评论翻页目前返回来源业务错误，因此自动首采只保存公开详情页中的评论，页数预算为 1。来源仍有后续评论时，接口的 `collection_complete` 保持 `false`，页面显示“已获取部分评论”；不能将采到的首页条数当作全部评价。没有来源日期时保持空值。

页面入口是“商品监测 → 打开商品 → 评论”。“刷新”读取已入库数据，不会发起新的来源请求。店铺的粉丝、累计已售、视频数来自档案采集，与商品样本统计分开。

`deployment/Dockerfile.review-coverage` 在已核对的当前镜像上仅更新评论衔接文件，保留同时上线的其他功能。`deployment/rollout_review_coverage.py` 使用共享发布锁，核对两名 Worker 的原镜像和当前 Compose 配置后逐个替换，记录原镜像与修复提交；不重建数据库、队列、API 或分析服务。发布前需运行评论存储、补采、异步处理器相关的隔离数据库测试。
