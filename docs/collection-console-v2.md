# 采集控制台扩展版

入口为 [采集管理](https://shopscope-monitor.top/#collections)、[采集监控](https://shopscope-monitor.top/#collection-monitor) 和 `#tasks` 任务明细。系统复用现有 FastAPI、MySQL、RabbitMQ、Redis、Scheduler、Worker 与三个分析角色。

## 开始采集

“开始采集”支持四种操作，必须选择明确范围和服务器允许的采集器：

| 操作 | 资源范围 | 后续工作 |
| --- | --- | --- |
| 导入新店铺 | 美区 TikTok Shop 公开店铺 HTTPS 链接 | 身份确认后产生商品发现和档案任务 |
| 扫描店铺商品 | 搜索并勾选现有店铺 | 按分页预算发现商品，追踪后续分页及详情 |
| 采集商品详情 | 搜索并勾选现有商品 | 更新公开详情、规格、图片、内容及按配置保存基线 |
| 采集商品评论 | 搜索并勾选现有商品 | 按分页预算采集公开评论并追踪后续页 |

链接会清除查询参数与片段，只接受当前适配器支持的公开店铺入口。相同归一化种子在同一天复用原始任务，界面显示新建和复用数量；已有店铺重新扫描商品时应选择“扫描店铺商品”。

资源选择支持名称、平台 ID、内部 ID 搜索，跨页保留选择，不可用项显示原因。单次最多 100 个资源，实际还受调度批次预算限制；分页上限不能超过服务器配置。同资源、同类型的活动采集会阻止重复启动和补采。提交只创建持久任务，HTTP 不访问来源网站；同一 UUID 的重试复用原始提交结果。

批次详情分别显示根任务、后续任务与补采任务。根任务完成后若分页或详情尚未结束，批次继续显示等待或运行。复用历史根任务时，不将未回溯的旧任务链冒充完整历史。

## 计划与恢复操作

周期计划支持店铺档案和商品快照，分别最短一小时和一分钟，最长七天。单次计划派发一次后停用。计划支持名称搜索、类型/状态筛选、编辑、立即运行、执行历史和可逆归档。

仅修改名称或重新提交相同周期，不改变下次派发时间。更改已启用周期后，下一次安排在修改时刻加新间隔；手动运行周期计划后，下一次为本次执行时刻加间隔。遗漏周期合并，前一执行及其关联补采仍活跃时不继续堆积新执行。归档停止后续派发并禁止新增执行和关联补采，已有任务继续完成；恢复后保持停用。

全局暂停持久化在 MySQL，在来源任务领取边界生效。已有租约允许完成，本地变化检测和报告可以继续。人工恢复不会清除来源保护性冷却。

整批取消持久化取消请求，每次处理最多 100 个待执行任务，剩余由 Scheduler 有界清理。领取边界会阻止已取消批次的独占任务开始，运行中任务可完成。同一任务由其他有效批次共享时继续执行；批次等待关联活动任务结束后完成取消。清理按最近检查时间轮转，共享任务不会挡住后续批次。取消已完成批次为无操作，不改写成功或失败历史。

单任务只允许取消无活动租约的待执行、重试等待或已放弃状态。六类来源任务均支持补采，创建新任务并保留原始尝试与断点；重复提交同一原任务只创建一个直接补采。全部所属批次取消后，不再创建新补采。写操作复用现有 API 权限，令牌仅在页面内存保存；审计只记录固定动作码和安全结果。表单暂存、搜索和选择保留在页面会话；提交期间禁止关闭与重复提交。

## 完整窗口监控

默认展示来源采集，可切换本地处理或全部任务。15 分钟、1 小时、6 小时、24 小时采用最近完整分钟，起点包含、终点不包含，并展示统计截止时间。成功率按完成尝试计算，重试分别计数。

完成事实与源任务同事务写入，后台将唯一尝试投影到分钟汇总。计数、成功数、错误分布和平均耗时准确；P95 为直方图桶上界近似，界面明确方法与误差。后台每批最多处理 500 条历史和 500 条待投影事实，保留可恢复游标，较小 ID 的迟完成不会被水位跳过。监控派生事实和分钟记录保留七天。

HTTP 只读已发布统计、最多 12 条近期失败及 200 个运行租约，不再读取两万条历史尝试。准备中显示未知值；过期、失败保留上次结果并显示时间。队列读取已有独立摘要。前端每 15 秒更新可见页面，隐藏或离开后停止读取。

Worker 和 Scheduler 每 10 秒上报心跳，空闲进程也上报。30 秒标记过期、60 秒离线、注册保留十分钟。预期进程数可识别两个 Worker 减少为一个；界面区分心跳、连接、就绪与调度进展。调度超过至少 120 秒或三个周期未成功时告警，Redis 不可用显示未知。

## 告警闭环

独立后台每 10 秒按固定一小时来源采集规则评估，切页和选窗不改变持久状态。支持未确认、已确认、已恢复及全部筛选，以及触发、确认、恢复和重开事件。重复观测只更新时间；重开清除上次确认。心跳未知、统计准备中/过期或失败率样本不足时，不将证据缺失当作恢复。页面展示条件可判断性与评估更新时间。当前未配置外部通知渠道。

## API 与升级

管理前缀 `/api/v1/collection-management`：新增 `GET /resources`、`GET/POST /launches`、`GET /launches/{id}`、`POST /launches/{id}/cancel`、`POST /plans/{id}/archive` 和 `/restore`，保留控制、计划、运行、任务取消/补采及审计接口。计划支持名称、类型、启用及归档筛选，批次按类型筛选；列表采用倒序游标，资源、任务、历史单页最多 50 条，数据库 ID 以字符串传递。

监控为 `GET /api/v1/collections/monitor?window_minutes=60&task_group=source`。告警为 `GET /api/v1/collections/alerts?status=active`、`GET /{id}/events` 与 `POST /{id}/ack`，确认请求体为 `{}`。

升级先执行 012、013、015、016、017、018 对应增量脚本的 `--execute`，并以 `--check` 验证；014 由独立认证改造保留。012 历史 SQL 不改写，015 为既有计划增加归档字段，016/017/018 分别增加监控、单次批次和告警表。不会清空来源数据。

确认所有尝试写入器切换后，执行 `python -m scripts.collection_monitor_rollups --reconcile` 固定重扫最近 25 小时。它保留已有事实与计数，唯一键去重，可修补旧写入器或回滚期间的缺口。等待 `--status` 的回填完成和新代数发布，再检查三个分组 `statistics.ready/status` 与告警评估时间。

`deployment/release_read_models.py` 包含增量迁移、候选只读检查、写入器版本确认和回填入口，切换失败恢复已有应用角色。部署不创建采集计划或访问来源网站。`tests/serve_collection_console.py` 使用本机合成数据与数据库派生后台，不启动来源 Worker 或消息队列。

验收包含真实 MySQL 并发启动/补采、源写回锁顺序、重复领取、共享批次同时取消、清理公平性、迟完成与回填幂等、告警并发确认与恢复，以及浏览器资源选择、草稿、慢提交保护和移动布局。[首版发布证据](evidence/collection-console-release-20261017.json) 保留初版抽样统计的历史边界。
