# 店铺与商品图片采集设计

当前要解决两件事：让店铺 Logo 的完整功能发布到线上，并让商品先获得可用封面，再逐步补齐相册与介绍长图。图片采集不能依赖所有价格和 SKU 详情先成功，也不能用一个“待采图”解释所有缺口。

本文件是基于真实线上诊断的目标设计。本文列明已修复代码和仍需实现的链路，不能据此认为全部方案已经上线。服务器发布继续由原发布任务统一执行。

## 分开管理四种图片

| 目标 | 权威来源 | 数据落点 | 完成口径 |
| --- | --- | --- | --- |
| 店铺Logo | 经身份验证的店铺档案 `shop_logo` | 复用 `Shop.logo_url`、档案快照和字段状态 | API返回真实Logo，已发布前端生成图片元素，并有实际加载成功证据 |
| 商品封面 | 店铺列表封面优先，详情首图补充 | `product_images`，保留 listing/detail 来源 | 商品有当前可展示的封面链接；不要求完整详情先成功 |
| 商品相册 | 经商品、店铺、市场身份校验的详情相册 | `product_images` 与相册完整性状态 | 该响应内全部图片身份成功解析，未丢弃未知源行或因上限截断 |
| 介绍长图/尺码图 | 商家介绍的已验证图片节点 | `product_contents.sections` | 介绍内已知图片引用按原顺序保留，和相册覆盖分别统计 |

店铺首字母是占位，不能算Logo；买家评论图片不进入商家相册；纯文字介绍不需要为了凑覆盖率补一张图片。所有“链接已保存”与“浏览器实际加载成功”分别统计。

## 采集与补采顺序

1. 先核对店铺档案的006迁移、模型、采集器、API和前端是否进入同一发布版本。小规模验证Logo实际加载，再处理剩余店铺。
2. 优先重放确实保留过图片字段的历史公开证据。旧投影没有图片字段时，明确记为不可离线恢复。
3. 对缺封面的店铺安排图片专用列表刷新，一页为多个商品补封面；不为每个封面重复取完整详情。这个任务只写图片与媒体状态，保留已有价格、SKU、业务版本和历史基线。
4. 对仍缺封面或需要补相册的商品，安排独立图片详情任务。先校验商品ID、店铺ID、市场、最终URL及响应业务状态，再独立提取图片。
5. 正常详情请求同时产生业务资料、相册和介绍投影。同商品已有可合并的在途请求时，媒体任务跟随其结果，减少重复请求。
6. 链接过期或全部候选加载失败时进入URL刷新流程，保持图片身份与历史证据，不将一次浏览器错误直接标成全站无图。

图片专用详情解析应与价格、SKU合法性解耦。验证页、登录页、错误商品、跨店铺跳转及业务错误不属于“源端无图”。不通过任意递归搜索页面URL来猜图片来源。

## 解析与旧图保护

解析结果需要明确携带 `source_path`、`parse_status`、源行数、有效图片数、无效行数、图片集合是否完整，以及候选地址是否截断。

| 解析结果 | 判定 | 持久化动作 |
| --- | --- | --- |
| complete | 已知图片数组全部检查，所有图片身份均有合法候选，未截断图片集合 | 更新相册顺序，可将本次确实未出现的旧图片失活 |
| partial | 部分行无法识别、主图URL全部无效或图片集合超限 | 增补可确认图片，保留原有其余图片，不声称相册完整 |
| source_empty | 已验证成功响应中的已知图片数组明确为空 | 保留旧资料及时间，记明确空观察并进入长冷却 |
| source_missing | 预期字段未出现或无法确定该页提供了此字段 | 保留原图，记录结构缺口 |
| unsupported | 字段类型或来源结构与已确认合同不一致 | 保留原图，进入待适配状态，保存白名单结构诊断 |

同一URI的CDN镜像或重复行只算同一张图片，不降低图片集合完整度。候选地址上限与图片数量上限分别记录。截断备用地址不等于漏掉图片身份；截断图片身份集合则不能宣称完整相册。

列表封面可立即用于展示，但不能作为详情相册已完成的证据。历史记录没有完整性证明时标记为未知；新任务只有在成功观察记录明确证明完整后才可跳过。

## URL候选与加载回退

保留原图和缩略图的有序候选，优先使用平台URI作为图片身份。URI缺失时保守处理，未经来源验证不能随意删除查询参数后合并不同图片。

- 商品列表依次尝试缩略图候选、原图候选；详情大图优先原图候选。
- 每个元素记住已尝试URL，去重并限制次数，避免 `error` 回调循环。
- 每类最多保留8个URL，单图片候选JSON最多64 KiB；超限记录截断，始终保留优先级最高的合法候选。
- 现有 `image_url`、`thumbnail_url` 保持兼容；新增候选字段为空时仍可读取旧记录。
- URL变化只更新媒体资料，不推进商品价格、SKU或业务内容版本。
- 所有候选耗尽后显示“图片加载失败”；没有链接时显示其真实采集状态。

默认保存引用，不批量下载图片二进制。后续若做可访问性验证，使用独立低频验证队列，检查响应类型和有限响应体，不开放任意URL代理。CDN链接过期、单浏览器网络失败与TikTok入口风控分别处理。

## 任务、状态与有限重试

### 状态来源

`crawl_tasks` 继续作为任务和尝试历史的权威记录。新增轻量媒体目标状态，使“有链接”“相册完整”“任务排队”各有依据。

建议新增 `image_collection_states`：通过可空 `shop_id` / `product_id` 外键及CHECK保证每行只属于一种资源；目标为 `shop_logo`、`product_cover`、`product_gallery`。分别对 `(shop_id,target)`、`(product_id,target)` 建唯一约束。市场归属由关联的店铺或商品校验。

| 字段组 | 必要内容 |
| --- | --- |
| 身份与目标 | shop_id / product_id、target、来源类型、解析版本 |
| 观察结果 | parse_status、source_count、valid_count、invalid_count、image_set_complete |
| 时间与失败 | last_attempt_at、last_success_at、next_refresh_at、last_error_code、response_status |
| 调度归属 | active_task_id、refresh_round、refresh_window_start、关联资源租约 |
| 来源证据 | source_url、response_hash；公开指标只暴露脱敏状态，不返回请求凭据 |

字段、表、索引用途均给中文注释。`product_images` 仅增量增加原图与缩略图候选JSON列。007迁移编号留给图片链路，避开原任务的006店铺档案迁移；具体DDL须随实现和兼容验证一起生成，本次未执行这些DDL。

### 去重与恢复

规划器在同一事务锁定目标状态，确认没有活动媒体任务、已到刷新时间，才分配下一轮稳定任务键。键包含资源、目标、解析版本和持久刷新轮次，不能使用随机时间制造无限任务。

普通详情与媒体请求共用商品资源租约，已在途的详情负责交付所需媒体结果。等待资源不计为站点请求失败。保留原任务及尝试历史，不删除旧key、不清空队列、不重置已用尝试数。

网络错误复用既有有界重试；访问受限复用现有市场暂停与资源冷却；字段未识别等待适配；明确无图长冷却；候选全部失效安排URL刷新。建议同解析版本每资源每天最多3轮刷新，轮次间按1小时、6小时、24小时递增冷却；这是待实现的默认策略，不代表已经启动。

### 店铺公平与资源份额

维持现有两台Worker、一秒全局请求间隔、HTTP队列高水位64及本地计算队列高水位16。先按任务目标分配份额，再按店铺轮转，每轮每店先发1–2个，避免按商品ID或大店任务总量长期垄断。

建议普通采集与媒体共享请求槽位各占约50%；媒体内优先分配Logo和缺封面任务，同时为相册与介绍保留固定份额。空闲类别将额度让给其他类别，不让任何一类无限饿死。待调度任务留在数据库，消息队列只保存可控数量的就绪通知。

两秒间隔理论最多1,800请求/小时。若16,378个待办各只请求一次且独占请求槽，最低约9.1小时；占一半槽位则最低约18.2小时。该计算不含网络、重试、验证页冷却或其他请求，不是预计完成时间。提高同一出口的Worker数不能突破共享闸门；列表一页覆盖多个封面才是在现有限制下减少请求的主要方式。

## API、页面与验收指标

API分别返回媒体链接、目标采集状态和可访问性证据。列表仅批量读取当前页商品状态，不能为每行执行一次全库状态统计。聚合状态按店铺缓存，显示统计时间，不把过期缓存标成实时。

页面使用“未安排”“排队补图”“正在补图”“等待重试”“暂时受限”“来源未提供”“待适配”“图片加载失败”等准确标签。已有封面、相册未完整时可以显示商品图，同时继续显示相册状态。实现信息放在运维详情中。

按全站和每家店铺分别展示：总商品数、封面链接覆盖率、相册完整覆盖率、未调度/排队/重试/失败数量、字段缺失/不支持/明确空数量。浏览器加载样本的成功率注明样本数与时间，不能套用为全部商品链接可访问率。

店铺Logo以店铺为分母，商品封面以所有已确认商品为分母，不能仅用成功详情群体美化整体覆盖。介绍图片以已观察到含图片的介绍为分母，纯文字介绍不进入缺图队列。

## 店铺Logo发布检查

1. 统一合入006迁移、店铺档案模型、处理器、调度、API与 `shopAvatar`。仅部署本分支旧Shop模型不能带出原D目录尚未合入的Logo功能。
2. 先只读检查服务器006迁移状态；按其增量脚本补齐，不导入整个本地数据库。
3. 已有100家本地资料仅通过安全、幂等的证据导入器按平台店铺ID复用；没有经过验证的导入器时走正常店铺采集任务。不能搬运本地自增主键或覆盖线上任务历史。
4. 发布前检查API、Worker、Scheduler的能力版本。图库解析与任务模式匹配后才入新任务。
5. 核对已有前端、状态模块的只读挂载目录；发布新版时同时更新或取消旧覆盖，避免新镜像仍运行旧文件。更新公网OpenAPI声明。
6. 真实GET确认店铺API返回Logo和观察状态，再确认公网JS生成图片元素，最后验证图片 `naturalWidth > 0`。仅HTTP200、存在数据库列或本地截图都不足以验收线上Logo。

## 本次已经落地的代码修复

本次在独立工作树修复相册正确性，不改变服务器或数据库结构：

- 图片候选增加可兼容的 `source_complete` 证据；无效源行或图片集合截断会将本次结果标为不完整。
- 不完整相册只增补，保留已有封面与顺序；完整非空相册才允许将未出现的旧图失活。旧证据缺字段时保守处理。
- 列表封面不能让详情相册任务跳过；只有成功任务中的明确完整性证据才可用于跳过。
- 正常详情和补采检查点分别记录 `images_upserted` 与 `gallery_complete`，不将一张图等同于完整相册。

本次整套回归在本机随机 MySQL 8.0.43 测试库和独立 Redis 中 **443项通过、无跳过**，测试数据和临时服务已清理。结果日志为独立工作树的 `data/samples/image-design-regression.log`，不进入Git；这不代表新代码已经部署到截图中的网站。

多候选URL持久化、目标状态表、店铺公平、批量封面刷新和Logo统一发布仍属于上面的待实现设计，本次未据文档声称它们已经上线。
